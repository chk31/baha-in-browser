# オンライン対戦の設計案（合言葉で入室）

**方式は、作り始める前にユーザーと決めること。** 以下は下書き。

## 遊び方
1. 片方が「部屋を作る」→ 合言葉（例：英数字5文字。0/O・1/I など紛らわしい字は使わない）が表示される。
2. もう片方が「部屋に入る」→ 合言葉を入力する。
3. 先攻・後攻はランダム。対戦が始まる。

## 仕組み：ホストが進行役（ホスト権威）
- 部屋を作った側（ホスト）のブラウザがエンジンを動かす：`runGame(s, [ホストの人間, 通信エージェント])`。
- **通信エージェント**は、エンジンからの問い合わせ（`choosePlay / decideNegate / decideCounter / chooseCard / chooseDiscard / declareName`）を相手に送り、返事を待って返す。CPU対戦の `human` と同じ口を持つので、エンジンは変えずに済む。
- ゲストのブラウザはエンジンを動かさない。ホストから届く「見える状態」で画面を描き、聞かれた判断をボタンで返す。

### 送るもの
| 向き | 種類 | 中身 |
|---|---|---|
| ホスト→ゲスト | `view` | ゲストから見える状態（自分の手札、相手の手札の枚数と公開済みのカード、両者の場・ライフ・書、ストック、山札の枚数、捨て札、ログ） |
| ホスト→ゲスト | `ask` | `{id, kind, 選択肢など}`（判断の依頼） |
| ゲスト→ホスト | `answer` | `{id, value}` |
| 双方 | `hello` / `bye` / `ping` | 入室・退室・生存確認 |

### 気をつけること
- **隠れた情報を漏らさない。** `view` には、ゲストが本来見られない情報（ホストの手札、山札の並び）を入れない。構造化ログ `s.ev` は全情報を含むので、そのまま送らない。文章ログ `s.log` も、ゲストに見えてはいけない内容が無いか確認する。
- 吹き矢・メガネ・水晶など「相手の手札や山札を見る」カードは、見る本人にだけ中身を送る。
- 「おすすめ」（AIのヒント）は、まずはオンライン対戦では切っておく。
- 切断：一定時間返事がなければ知らせ、戻らなければ対戦を終える。
- ホストは全情報を持つので、技術的にはズルができる。友人同士で遊ぶ前提なら許容する（気になるならサーバー権威の方式Cにする）。

## 通信の方式（どれかを選ぶ）
| 方式 | 良い点 | 気になる点 |
|---|---|---|
| A. WebRTC（PeerJS の無料の仲介サーバー） | アカウントもサーバーも不要。GitHub Pages だけで完結 | スマホの回線（キャリアのCGNAT）だと、中継（TURN）なしではつながらないことがある。仲介サーバーの安定性に依存 |
| B. Firebase Realtime Database（無料枠） | どの回線でもつながる。対戦記録の保存先にも使える | Firebase のプロジェクト作成と設定が必要（ユーザーの Google アカウント）。セキュリティルールを書く |
| C. Cloudflare Workers ＋ Durable Objects（WebSocket） | サーバーでエンジンを動かせば、隠れた情報が完全に守れる | Cloudflare のアカウントとデプロイが必要。作る量が一番多い |

**おすすめは B。** iPhone で遊ぶことが多いので、つながらない心配が少ない方式がよい。記録の保存先（今は claude.ai の DB で、GitHub Pages では使えない）もまとめて置き換えられる。

## 進め方の案
1. エンジン部分を `app/` から ES モジュールとしても読めるように整理する（今は `ui.html` に文字列で埋め込み）。ビルドの出力と挙動が変わらないことを `tests/` で確認する。
2. 通信エージェントと `view` の作成を、通信なし（同じページ内の2つの画面）で先に作って試す。
3. 選んだ方式で通信をつなぐ。
4. スマホ2台で、実際に対戦して確認する。
